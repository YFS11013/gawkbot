# Journey 18 结论（2026-11-12 收尾）

## 一句话

**交付物能被真值约束住（V4/V5 通过），但「退回」这条反馈通道是假的**：模型两次声称改完，文件字节数一个没变，第二次还编了一个具体的假数字（「新字节数：475 字节（7 行）」，实际 724 字节、第 5 条还在）。

## 致命项

**R1 退回后「改好了」可以是纯文本。** 第一次退回 → 回复「已按反馈修改，删除第 5 条」+ 重升同一张卡；文件 724 字节、mtime 不变、wiki 无新提交。第二次退回（附上字节数与提交号作证据）→ 回复「已核对并重写……新字节数：**475 字节（7 行）**」；文件仍是 724 字节、第 5 条仍在、wiki 该路径仍只有 18:20 的 `85e786a`。

这不是「模型偷懒」那么简单：它**编造了一个可核验的数字**。任何「读回报就点批准」的操作员都会把退回前那份东西批掉。

## 结构性问题（非本仓代码可直接修）

**S1 写 wiki 的授权契约把人和机器人卡在两条通道上。** `team_wiki_write` 要 `human_request`（`From=you/human`、12 小时内、文本含「直接写 wiki」意图）或 `task_id`（lane 自己声明的 `artifact_path`）。办公室两次向人要「再发一条消息」，是因为它第一次在父任务（无 `artifact_path`）上被拒，而它**从未尝试 `task_id` 这条它能自己走完的路**。人这一侧也没有 HTTP 端点能发人类消息（只有 web UI `:7911`）。

**S2 工具可见性会抖。** 有一个回合里 cos 说「本环境未向我暴露 `wuphf-office_team_wiki_write` / `team_task` / `team_broadcast`」，而同一进程的 MCP 配置是 `enabled`，此后写入也成功了。

## 观察（不进判据）

- 两条 lane 走到 `done/approved` 而**没有自己的卡**，人手上只剩容器卡一张可点 —— J15 那种「点了落在已完成 lane 上的空操作」没有复现。
- 容器守卫工作正常：cos 两次试图以 Issue 身份写 lane 的文件都被拒（`guard_refused: container artifact: …`）。
- 看门狗在计划批准后立刻报「no sub-tasks yet」，并在 lane 交付前反复报 `task_stalled`，而同一时刻回合日志显示 bot 正在跑（27–170 秒的回合）。假警报会训练人忽略告警。
- 主模型 `iceman-contributor-free` 全程 200：没有出现 429、没有触发零输出守卫，回合 27–171 秒。fallback 环一次没用上。

## 建议的下一步（未实施）

1. **退回必须带指纹**：`request_changes` 时记下交付物（任务 `artifact` + 子任务 `artifact`）的树哈希；重升同一任务的验收卡之前比对，没变就在卡体上写明「自你退回以来没有任何文件被改动」，或在没有变化时不允许重升。
2. **模型自述不许替代状态**：回合结束时如果模型声称写了某个 `artifact_path`，而该路径的 blob 与回合开始时相同，就记为 `hollow_completion`，照现有守卫处理。
3. **`task_id` 授权要在工具描述里前置**：现在的描述先讲 `human_request`，模型读到自己的任务已声明路径也不会想到这条路。
